# Feature Specification: 需求池三项交互修复（可选项缓存 / 领取可见 / 目标带出内容）

**Feature Branch**: `002-fix-pool-claim-target`
**Created**: 2026-09-20
**Status**: Draft
**Input**: User description: "1.为什么每次都需要重新加载 团队项目、工作类型，每次重启服务或者无数据时才需要重新加载，否则禁止重复加载 2.领取入池为什么毫无效果，设为目标一样点击 3.设置为目标应该把需求的内容带出显示，而不是需要用户进行复制粘贴和复制"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 筛选可选项只在该拉的时候拉 (Priority: P1)

需求池的「团队项目 / 工作项类型 / 状态 / 指派给」四个筛选下拉，其选项来自 TFS 端的真实采集（项目清单 + 每个项目的类型与状态元数据）。今天用户每次切回「需求池」页签，这些下拉都会重新采集一次，表现为打开页签后长时间空转、下拉迟迟不可选，且每次都重复消耗 TFS 调用配额。

用户期望：**只有服务重启后第一次、或本地确实还没有这份数据时才采集**；已有数据时直接复用，不得重复加载。同时必须保留一条「手动重新采集」的逃生通道——用户在 TFS 上新建了项目/类型之后，要能主动刷新，否则缓存会变成新的"数据陈旧"问题。

**Why this priority**: 它是每次打开页签都会撞上的首要体感问题，且直接消耗外部系统配额；另两项缺陷只在特定操作时出现。

**Independent Test**: 打开需求池 → 切到「任务中心」→ 再切回「需求池」→ 观察下拉是否立刻可选、且后台未再发起采集；重启服务后再打开，观察是否采集一次。仅本条落地即可独立交付价值。

**Acceptance Scenarios**:

1. **Given** 本次服务已采集过一次可选项，**When** 用户在需求池与其它页签之间来回切换，**Then** 四个下拉保持已有选项（不空、不闪），且不再发起新的采集请求。
2. **Given** 服务刚重启、本地尚无可选项数据，**When** 用户首次打开需求池，**Then** 自动采集一次并填好四个下拉。
3. **Given** 可选项已缓存，**When** 用户点击「重新采集」按钮，**Then** 强制重新采集一次并刷新下拉，且按钮在执行期间给出进行中状态。
4. **Given** 采集发生过降级（部分项目取不到类型），**When** 用户查看面板，**Then** 仍能使用已获得的那部分选项，并看到一句说明原因的提示，而不是整块下拉为空。

---

### User Story 2 - 「领取入池」必须有看得见的结果 (Priority: P2)

需求列表每行有「领取入池」与「选为目标」两个按钮。今天点「领取入池」后，除了顶部一行一闪而过的文字，界面没有任何持久变化：需求行不标记、任务中心角标不变、按钮仍可再次点击，用户无从判断到底成没成，主观感受是"点了跟没点一样"。

用户期望：领取成功后，同一行立刻呈现「已入池」的持久标记（且刷新/轮询后仍然在），任务中心的已领取需求计数同步增加，按钮语义随之变为不可重复入池；若领取失败，则明确说失败原因，绝不静默。

**Why this priority**: 它让核心链路（领取 → 拆解 → 派发）的第一步在 UI 上"看起来是坏的"，直接阻断后续所有操作。

**Independent Test**: 在需求池中任选一条需求点「领取入池」，观察该行是否立刻出现已入池标记、顶部目标栏/任务中心计数是否同步；再点一次观察是否提示"已在池中"而非重复入池。

**Acceptance Scenarios**:

1. **Given** 需求池中有一条未入池的需求，**When** 用户点它的「领取入池」并成功，**Then** 该行立刻变为已入池状态（标记可见），且「任务中心」页签的已领取需求计数加一。
2. **Given** 该需求已在池中，**When** 用户再次点「领取入池」，**Then** 提示"已在池中"，列表与计数不发生重复变化。
3. **Given** 领取因连接或参数原因失败，**When** 用户点「领取入池」，**Then** 显示失败原因，该行**不**被标记为已入池。
4. **Given** 领取期间正在请求，**When** 用户观察按钮，**Then** 按钮显示进行中且不可重复提交，避免连点造成重复写入。

---

### User Story 3 - 「选为目标」自动带出需求内容 (Priority: P3)

今天在需求池点「选为目标」后，只是把目标编号挂到执行配置页的标题栏，表单里的标题/描述/执行 Prompt 全是空的，用户必须回到 TFS 复制需求正文再粘贴回来。

用户期望：选为目标后，执行配置页自动带出该需求的标题与正文内容（作为描述与执行 Prompt 的初始内容），用户只做微调即可发起执行；用户手改过的内容不被后续自动填充覆盖。

**Why this priority**: 它是效率优化，不阻断主链路，但每天重复复制粘贴的成本最高。

**Independent Test**: 选一条需求为目标 → 切到执行配置页 → 观察标题/描述是否已填为该需求内容，且不需要任何复制粘贴即可直接发起执行。

**Acceptance Scenarios**:

1. **Given** 用户在需求池点某条需求的「选为目标」，**When** 执行配置页打开，**Then** 标题与描述已填入该需求的标题与正文，执行 Prompt 亦以该需求内容为初始内容。
2. **Given** 用户已手工修改过执行配置的表单内容，**When** 用户又选了另一条需求为目标，**Then** 新目标的内容仍然填入（用户可通过明确的清空动作回到空白），且不会出现"改了一半"的混合内容。
3. **Given** 该需求在 TFS 上正文为空，**When** 选为目标，**Then** 描述区域留空并给出"该需求无正文"的说明，而不是显示空框让用户以为坏了。
4. **Given** 需求正文是富文本（HTML），**When** 填入描述，**Then** 显示的是可阅读的纯文本内容，而不是一整段原始标记。

---

### Edge Cases

- 采集缓存存在但**集合被切换**：不同集合的项目清单完全不同，切集合必须视为"无数据"重新采集一次。
- 采集缓存存在但**内容为空**（上次全项降级）：空结果不应被当成"已有数据"而永久锁死，应允许再次尝试。
- 并发：多个页签/多次进入同时触发采集时，只应发生一次真实采集，其余共享同一次结果。
- 领取的目标在 TFS 上正文字段极大或含附件引用：填充内容应截断到可读长度，不撑爆面板。
- 用户未选任何目标就打开执行配置页：表单保持空白，不报错、不乱填。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 对需求池筛选可选项（团队项目 / 工作项类型 / 状态 / 指派给）做**进程内缓存**：已有数据时不重复采集，仅在服务重启后首次、或本地无数据时自动采集。
- **FR-002**: 系统 MUST 在切换目标集合后，把该集合的可选项视为无数据并重新采集一次。
- **FR-003**: 系统 MUST 提供显式的「重新采集」入口，让用户能强制刷新可选项，并在执行期间显示进行中状态。
- **FR-004**: 系统 MUST 保证同一份可选项的并发请求共享一次真实采集，不得因重复进入而放大对外部系统的调用。
- **FR-005**: 系统 MUST 在采集部分失败时保留已获得的部分选项，并给出可读的降级说明。
- **FR-006**: 系统 MUST 在「领取入池」成功后于该需求行显示**持久**的已入池标记，并同步任务中心的已领取需求计数。
- **FR-007**: 系统 MUST 对重复领取做幂等呈现：已入池的需求再次领取时提示"已在池中"，不产生重复条目。
- **FR-008**: 系统 MUST 在领取进行中禁用该操作重复提交，并在失败时显示可读原因且**不**标记成功。
- **FR-009**: 系统 MUST 在「选为目标」后，把该需求的标题与正文自动填入执行配置页的对应字段，用户无需复制粘贴。
- **FR-010**: 系统 MUST 把需求正文富文本转为可读纯文本后再展示，并在正文缺失时明确说明而非留空框。
- **FR-011**: 系统 MUST 保证自动填充不破坏用户已手工编辑的内容：填充发生在"目标变更"这一明确时机，而非每次渲染。

### Key Entities *(include if feature involves data)*

- **筛选可选项（QueryOptions）**：团队项目 / 工作项类型 / 状态 / 指派人四组候选值，附采集时刻与降级原因；其生命周期与"目标集合"绑定，进程内只保留一份有效副本。
- **已入池需求（ClaimedRequirement）**：本地池中已领取的需求副本，用「编号@集合」作去重键；UI 需能按该键判断列表中某行是否已入池。
- **执行目标（Target）**：当前被选中的需求；切换它即触发执行配置表单的自动填充。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在同一服务生命周期内，第二次及以后进入需求池页签，四个筛选下拉立即可用（无需等待采集），且后台采集请求数**为 0**。
- **SC-002**: 服务重启后首次进入需求池，四个下拉在**一次**采集内填好；采集期间界面显示明确的状态而非空白。
- **SC-003**: 点「重新采集」后，下拉内容被刷新一次，且在完成前用户能看到进行中状态。
- **SC-004**: 「领取入池」成功后，用户在**同一屏内**（不刷新、不切页）就能看到该需求的已入池标记，任务中心计数同步变化；失败时同一屏内即可看到原因。
- **SC-005**: 「选为目标」后进入执行配置页，标题与描述已填好，用户在**零次复制粘贴**的前提下即可发起执行。

## Assumptions

- 目标 TFS 上的项目/类型/状态元数据在单次会话内基本不变，故进程内缓存的陈旧风险可接受；用户如需拿最新值走「重新采集」。
- 缓存只存在于服务进程内，服务重启即失效——这与用户"每次重启服务才需要重新加载"的表述一致，不做跨重启的磁盘持久化（避免陈旧数据固化）。
- 「已入池」判定以本地池快照为准，不额外增加对外部系统的读取。
- 需求正文取自 TFS 工作项的标准正文字段；若该字段为空，则按"无正文"处理而非回退到其它字段。
