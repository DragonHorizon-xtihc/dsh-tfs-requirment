# Feature Specification: 任务中心主对话框 + 编排主 agent + 共享简报复用

**Feature Branch**: `010-orchestrator-chat-shared-brief`
**Created**: 2026-09-29
**Status**: 待评审（speckit specify 产物）
**Input**: User description:
> 1. 任务中心「进行中」任务列表**右侧添加主对话框**，可以参考侧边对话(beta)；拆分任务后自动执行，
>    开始由**主 agent 逐一派发执行**，任务完成后**总结归纳**再执行下个任务；所有任务执行完成后，
>    **主 agent 做最终归纳总结**并更新状态、以及 TFS 需求和任务等需要更改的字段，并上传所有产物；
>    **主 agent 可以点击切换到子 agent，子 agent 可以切换回主 agent**。
> 2. 优先使用**绑定的任务**和 **mcp**。
> 3. 需要避免每个子 agent **重复造轮**，浪费 token、性能和时间。

需求澄清（用户已裁定，见 §零.3）：
- 主 agent = **插件为每条需求新建的专职编排 agent**（continuable 持久子会话），不是用户当前主会话；
- 「绑定的任务和 MCP」= 子 agent 优先复用**已绑定的看板任务上下文**（需求提示词 / 工作目录 / 前序任务结论 / 产物清单）
  与**角色冻结的 MCP + 技能集**，而不是自己重新检索、重新发现工具；
- 复用策略 = **共享简报（brief）+ 持久会话复用，两者都要**。

根因与宿主事实依据见同目录 `research.md`（全部带 `文件路径:行号`），本文只定义需求与验收标准。

---

## 零、问题定义

### 1. 现状（已核实）

- 任务中心是**纯表格**：只有任务行 + 动作按钮，执行过程要看必须打开「执行过程详情」弹层（`TaskDetailDialog`），
  而那是**只读时间线**，不能对话、不能接着指挥。
- 「派发」由**宿主编排器**（插件代码）驱动：`dispatch → launchRun → bindRun → run.result → settleTask →
  autoStartRunnable`（`src/host/api.ts:808-940, 1620-1666`）。**没有任何 LLM 参与"归纳"**：
  任务与任务之间只传递看板状态，前序任务读过的需求正文、探索过的代码库、踩过的坑，**下一个子 agent 全部重新来一遍**。
- 每个任务都是 **ONE-SHOT** 子 agent（`RequirementDispatcher.dispatch` → `client.start(provider, request)`），
  会话用完即弃 ⇒ 零上下文复用，这是「重复造轮」的结构性根因。
- 需求全部完成后的回写（字段 / 评论 / 附件 / 关联任务）已由 `RequirementFinalizer` 覆盖
  （`src/host/requirement-finalizer.ts`），但**总结文案是模板拼的**，不是主 agent 归纳的。

### 2. 目标形态

任务中心「进行中」页改为**左右分栏**：左 = 任务表（现状不变），右 = **主对话框**，里面是
**该需求的专职编排主 agent 会话**。用户看到的是「一个在替你盯这条需求的工头」：

- 拆解 → 自动执行 → 主 agent 逐个放行任务；
- 每个任务完成 → 主 agent 收到通知、**归纳成简短结论**并更新共享简报 → 放行下一个；
- 全部完成 → 主 agent 出**最终总结** → 更新 TFS 状态与字段 → 上传全部产物；
- 顶部可切换：**主 agent ↔ 任一子 agent**，子 agent 视图有一键「返回主 agent」；
- 每个子 agent 开工时拿到的是**同一份共享简报 + 本任务增量**，不再各自从零理解需求。

### 3. 已裁定 / 未决

| 项 | 裁定 |
|---|---|
| 主 agent 身份 | 插件按需求新建的 **continuable 编排子会话**（`startContinuable`） |
| 绑定的任务+MCP | 复用已绑定看板任务上下文 + 角色冻结 MCP/技能；不改用宿主 tfs MCP（避免绕过 WriteGuard 四道门禁） |
| 复用策略 | 共享 brief **且** 任务子会话按「需求+provider」复用（continuable 续跑） |
| 缺口 | `[NEEDS CLARIFICATION-1/2/3]`（research.md §九）：`subagent/end` 插件级可达性、provider 是否支持 continuable、token 收益未量化 |

## 一、用户故事与验收标准

### US1：任务中心「进行中」右侧内嵌主对话框

**As a** 在任务中心盯一条需求的用户，
**I want** 任务表右侧直接就该需求的主 agent 对话，
**So that** 我能边看任务边与编排 agent 对话，不必在弹层与表格之间来回切。

#### 验收标准

- **AC1.1（分栏布局）**：「进行中」子 Tab 改为左右分栏（左任务表 / 右对话框，可拖拽调宽、可整体收起）。
  「已完成」子 Tab **保持现状**（单栏），不引入对话框。
- **AC1.2（主 agent 会话）**：右侧默认显示**当前焦点需求的编排主 agent 会话**；切换焦点需求时右侧随之切换。
  未创建编排会话时显示「尚未创建编排会话」+「创建编排会话」按钮，**不静默显示空白**。
- **AC1.3（真实会话，非自绘日志）**：对话框必须渲染宿主真实会话内容
  （`renderFactorySlot('conversation.content', { variant:'embedded', … })`），含可输入框；
  **禁止**自己实现一套消息气泡来"假装"是会话。
- **AC1.4（会话绑定纪律）**：`sessions.retain()` 必须在**切换/挂载时**调用、`release()` 在**卸载/切换走时**调用，
  反复切换 20 次不泄漏引用（面板显示当前 retain 数用于自检）。
- **AC1.5（continuable 不可用则 fail-loud 降级）**：`startContinuable` 被 provider 拒绝时，
  面板显示可读原因（含 provider 名），并**保留**现有 one-shot 派发链路可继续工作；
  不允许"编排会话建不出来但按钮看起来能点"。

### US2：主 agent 驱动自动执行（逐一派发 → 归纳 → 下一任务 → 最终总结 → 回写）

**As a** 需求负责人，
**I want** 拆解后自动跑完整条链，且每个任务完成后有人归纳、全部完成后出总结并回写 TFS，
**So that** 我不必逐个点「派发执行」，也不必自己拼结论。

#### 验收标准

- **AC2.1（自动开始）**：拆解成功后，若该需求存在编排主 agent，则由主 agent 会话收到「开工」指令并**逐一**放行任务；
  并发上限仍受 `maxConcurrentRequirements` 约束（**不因引入主 agent 而放大并发**）。
- **AC2.2（完成后归纳）**：任一任务 `success` 收口后，主 agent 会话收到一条包含
  「任务标题 + 最终输出摘要 + 产物清单」的通知消息；主 agent 的回复被解析为**该任务的结论摘要**并落进看板。
  归纳失败/超时（默认 120s）**不阻断**流程：退回"无摘要"，下一任务照常放行。
- **AC2.3（共享简报增量）**：归纳出的结论进入需求级**共享简报**；后续任务派发时 prompt 只带
  「共享简报 + 本任务增量」，不再重复粘贴需求正文全文。
- **AC2.4（最终总结 + 回写）**：需求全部任务完成后，主 agent 会话收到「全部完成，请出最终总结」，
  其回复作为**结论评论**写入 TFS；随后按现有 `RequirementFinalizer` 完成
  状态流转、需求/任务字段更新、全部产物上传为附件。
  主 agent 总结失败/超时 → 回退到现有模板总结并**在报告中标注 "summary: template-fallback"**。
- **AC2.5（人工确认不被绕过）**：任一任务停在 `needs_confirmation` 时，主 agent **不得**继续放行后续任务
  （沿用 `src/host/api.ts:1621` 的既有门禁）；人工「确认通过」后才恢复。

### US3：避免每个子 agent 重复造轮

**As a** 在意 token / 时间成本的用户，
**I want** 同一条需求下的子 agent 共享已理解的上下文、复用持久会话，
**So that** 不再每个任务都重新读一遍需求、重新探索一遍代码库。

#### 验收标准

- **AC3.1（共享简报结构）**：需求级简报至少包含
  ① 需求标识与标题；② 工作目录绝对路径；③ 需求正文摘要（首次由主 agent 生成，≤ 1500 字）；
  ④ 已完成任务的有序结论列表（每条 ≤ 300 字）；⑤ 已产出产物绝对路径清单；
  ⑥ 本需求可用的 MCP/技能清单（取自角色冻结配置 `FrozenConfig.mcp/skills`）。
- **AC3.2（只注入增量）**：任务 prompt = 【共享简报】+【本任务增量（标题/描述/任务 prompt）】+【执行纪律段】。
  实测口径：同一需求内第 2 个及以后任务的 prompt 中，**不得再次出现需求正文全文**。
- **AC3.3（会话复用）**：同一需求 + 同一 provider(preset) 的连续任务复用同一个 continuable 子会话，
  后续任务以 **inbox 消息**续跑（`sendMessage`），不新建会话。
  复用会话的 `childId` 与 `parentSessionId` 落看板（可观测、可切换）。
- **AC3.4（完成观测与降级）**：复用会话的任务完成以 `ctx.on('subagent/end')`（匹配 `info.id === childId`）为准；
  未收到事件时用 `sessionQuery.observeSession(childId)` 轮询兜底；两者都拿不到且超过
  `taskSessionSettleTimeoutMinutes`（默认 30 分钟）→ 该任务按 `failed` 收口并给出可读诊断，
  **不允许任务永久停在 running**。
- **AC3.5（可观测收益）**：任务详情里展示本次 attempt 的 `turn 数 / 工具调用数`（复用 `TaskTraceService` 的 `stats`），
  让用户能自己判断复用是否省了开销；面板不承诺具体比例。

### US4：主 agent ↔ 子 agent 双向切换

**As a** 想介入某个具体任务的用户，
**I want** 在主对话框里点一下就能切到那个任务的子 agent 会话，并能一键切回来，
**So that** 我既能总览也能下钻，且不用回到别处去找。

#### 验收标准

- **AC4.1（切换条）**：对话框顶部是一条会话切换条：`主 agent` + 每个有会话的任务一项
  （显示任务标题 + 执行态药丸），点击即切换；当前项高亮。
- **AC4.2（子 → 主）**：子 agent 视图顶部有「← 返回主 agent」按钮与面包屑，点击回到主 agent 会话。
- **AC4.3（状态可见）**：切换条如实反映每个任务是否已产生会话；**没有会话的任务项不可点**（禁用 + tooltip 说明），
  不给出一个点了没反应的按钮。
- **AC4.4（子会话只读性）**：ONE-SHOT 子 agent 会话结束后不可再输入（宿主语义）；UI 不伪装成可继续对话，
  而是显示「该任务会话已结束」+「追问」（走现有 `followUpTask`）。
- **AC4.5（侧栏兜底入口）**：提供「在侧边栏打开」按钮，走宿主
  `sidebarRight.openResource(subagentChatAddress(addr), { kind:'subagentchat', preferNewPane:true })`；
  宿主无该服务时按钮隐藏（不报错、不留死按钮）。

### US5：优先使用绑定的任务与 MCP

**As a** 已配好角色与工具集的运营者，
**I want** 子 agent 直接用我绑定好的任务上下文与 MCP 工具，
**So that** 它不会自己去另找一套工具或另建一份理解。

#### 验收标准

- **AC5.1（冻结配置即工具面）**：任务派发的 `toolFilter` 与技能范围严格来自
  `FrozenConfig.mcp/skills`（缺省回落角色 `defaultMcp/defaultSkills`），
  与现状一致（`src/host/api.ts:581-590`）；**本特性不改变**该口径。
- **AC5.2（简报里显式列出可用 MCP/技能）**：共享简报的第 ⑥ 段给出本需求可用的 MCP/技能名，
  并附一句「优先使用上述已绑定工具，不要自行寻找替代方案」。
- **AC5.3（不绕过写门禁）**：本特性**不**引入宿主 tfs MCP 作为子 agent 的 TFS 写入通道；
  TFS 写仍只有 `adapter.executeWrite` 一条过 WriteGuard 四道门禁的路径。

## 二、边界与不做的事（Out of Scope）

- 不改「已完成」子 Tab 的布局与交互。
- 不改 TFS 写门禁（WriteGuard 四道门禁）、不改幂等键与审计口径。
- 不改动 `RequirementFinalizer` 的字段映射规则，只在"结论文案来源"上增加主 agent 总结（AC2.4）。
- 不做"主 agent 自行决定拆解"——拆解仍由现有 `decomposeRequirement` 完成，主 agent 只负责放行/归纳/总结。
- 不承诺 token 下降比例。

## 三、边缘情况

| # | 场景 | 期望行为 |
|---|---|---|
| E1 | 需求从未派发过（无 parentSessionId） | 「创建编排会话」按钮不可用，提示"先在会话里发起一次执行" |
| E2 | 宿主无 `sessions` 服务或 `renderFactorySlot` 缺失 | 右侧显示**可读降级原因** +「在侧边栏打开」；不白屏、不抛错 |
| E2b | 宿主装配缺 `session` 作用域适配器（未装 `ui-session`） | 渲染器在**父条目**组装阶段抛 `SlotAssemblyError`（`ui-renderer/src/client/scoped-slots.tsx:580-586`），条目被降级摘除（面板消失）。web profile 自带 `ui-session`，实测不触发；此条为**已知前置条件**，登记而非隐藏 |
| E3 | 编排会话所在子会话被清理 / 冷读失败 | 显示「会话不可读（原因）」+「重建编排会话」按钮；看板状态不受影响 |
| E4 | 任务归纳超时（主 agent 卡住） | 记事件 + 面板提示"归纳超时，已按无摘要继续"；任务链继续 |
| E5 | 复用会话期间插件重启 | 重启后按 attempt 上持久化的 `childId` 冷恢复；对账（既有 `reconcile()`）把悬空任务标失败 |
| E6 | 同一需求并行派发到同一 provider 的两个任务 | **禁止**复用同一会话并发投递；第二个任务排队等前一个收口，或另起会话（由 `reuseTaskSessions` 策略决定，默认排队） |
| E7 | 切走任务中心 Tab | 分栏不卸载（沿用既有 Tab 保活），但**释放**当前 SessionReference，切回时重新 retain |
| E8 | 主 agent 会话里用户手动发消息 | 允许；插件不拦截用户输入，仅追加自己的通知消息 |

## 四、成功标准（可验证）

1. 任务中心「进行中」页右侧渲染出**宿主真实会话**（能输入、能看到模型回复），切换主/子会话 20 次无引用泄漏。
2. 一条 3 任务需求从拆解到全部完成，**人工只需点一次**（拆解后自动跑完），
   期间每个任务完成后主 agent 会话产生一条归纳消息。
3. 全部完成后 TFS 需求收到**主 agent 写的结论评论** + 全部产物附件 + 状态/字段更新（可在 TFS 页面上核对）。
4. 同一需求第 2/3 个任务的 prompt **不含需求正文全文**（单测断言）。
5. 三道 `tsc`（host / client / tests）+ `vitest` 全绿；`tsdown` 构建通过。
